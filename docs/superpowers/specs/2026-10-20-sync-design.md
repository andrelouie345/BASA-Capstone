# Sync (upload, review, merge pull, offline sign-in) — design

Date: 2026-10-20. Status: approved in brainstorming, awaiting written-spec review.
Related: CLAUDE.md *Offline and sync*, README *Keeping BASA up to date* and 2b,
`docs/superpowers/specs/2026-10-20-version-check-design.md`,
`lib/core/console/commands/pull_commands.dart` (today's one-way pull).

## Goal

A tutor works offline for days, comes online, and syncs. Their new and edited
records reach the server without id clashes or silent overwrites, after the
tutor confirms what goes up and (unless auto-approved) a coordinator approves
it. The device then holds a fresh copy of the user's scope. Nothing local is
lost unless someone explicitly discards it. The owner of the device can sign in
offline to keep working.

Out of scope: server-to-server sync (cloud <-> LAN), incremental pull, splitting
large uploads, moving another device's upload onto a new device, encrypting the
local database, pushing offline login attempts to the server, making today's
online-only admin work available offline.

## Decisions (owner, 2026-10-20)

| Topic | Decision |
|---|---|
| Review step | Both: the tutor reviews and confirms on the device, and an admin/coordinator approves on the server. A per-school **auto-approve** setting skips the server approval. Uploads by an admin/coordinator apply immediately. |
| Approval unit | The whole upload. Reject sends it back with a reason; the tutor fixes and syncs again. |
| Conflicts | Detect and stop. Each edited record carries the server version it was based on; if the server changed since, the upload is held and the conflicting records are listed. |
| While pending | Records in a pending upload are read-only on the device. New work is allowed (next upload). The tutor can withdraw a still-pending upload to change it. Uploads never chain. |
| Servers | One server per deployment: a device syncs with the server it is configured for (cloud or LAN). No server-to-server sync. |
| Offline sign-in | Yes, for the device owner only, within an adjustable window (default 14 days). Sync always needs a live online sign-in. |
| Mechanism | Approach 1: one upload package per sync, applied by a server function in one transaction. (Rejected: staging copies of every table; replay through the approver's app, which is not atomic.) |
| Lost device | Physical problem outside BASA. The tutor signs in on another device and pulls; unsent work is lost; pending uploads stay approvable. No special feature. |
| Updates | A database/app update that requires an app update is done only when all work is finalized (README checklist, section 8). |

## 2. Server (one migration)

New migration, newer than `20261020010000`. Header:
`App update required on all devices: yes` (devices must run the sync release;
see section 8). Ends with its `basa_migrations` insert; its id is added to
`lib/core/release.dart` in the same commit. RLS raised in the same file.

### 2.1 `row_version`

Added to the 18 tables: `row_version bigint not null default 1`. A
`BEFORE UPDATE` trigger sets `NEW.row_version = OLD.row_version + 1`. Pulls copy
it to the device. (Several tables have no `updated_at`, and client-stamped times
are not a reliable version, hence a dedicated column.)

### 2.2 `sync_uploads`

| Column | Notes |
|---|---|
| `id` | bigint identity |
| `client_upload_id` | uuid, unique; generated by the device (retry-safe) |
| `uploader_id` | uuid, default `auth.uid()`, references users |
| `school_id` | bigint, references schools |
| `device_id` | uuid from the device's `sync_meta` |
| `release` | text, the device's latest migration id |
| `status` | `pending`, `applied`, `rejected`, `withdrawn`, `conflict`, `error` |
| `payload` | jsonb, the package (section 4) |
| `summary` | jsonb, counts per kind and section, written by the device; listings read only this |
| `reason` | text: reject reason or error message |
| `conflicts` | jsonb: `[{table, key, base_version, server_version, server_row}]`; a server-deleted row has `server_row = null` |
| `id_map` | jsonb: `{table: {"-5": 812, ...}}` after apply |
| `created_at`, `decided_at`, `decided_by` | |

RLS:
- insert: `uploader_id = auth.uid()`, `school_id` = the uploader's school, `status = 'pending'`, decision columns null.
- select: the uploader; admin/coordinator of `school_id`; superadmin.
- no update or delete grants for `authenticated`; anon gets nothing. Status changes only through the functions below.

### 2.3 Functions

- `sync_withdraw(p_id)`: the uploader, only while `pending` → `withdrawn`.
- `sync_reject(p_id, p_reason)`: admin/coordinator of the school or superadmin; `pending` only; reason required → `rejected`.
- `sync_apply(p_id)`: `SECURITY INVOKER`, so every row write goes through the caller's RLS and the existing CHECKs and triggers. Allowed callers: admin/coordinator of the school or superadmin; the uploader when the school's `sync_auto_approve` is on or the uploader is an admin/coordinator. Status must be `pending`.
  - Release guard first: refuses (status unchanged, clear message) when the package's `release` is older than an `app_update_required = yes` migration in `basa_migrations`: "re-sync from an updated device".
  - Then, inside one sub-block, walks the records in package order:
    - insert: drop a negative `id`, insert the row, record old → new id in the map. Foreign keys pointing at negative ids are rewritten through the map using a fixed list of FK columns (e.g. `aral_attendance.session_id`, `.enrollment_id`; `aral_checkin_answers.checkin_id`; part tables' `assessment_id`; the Phil-IRI children's parent columns). The exact list is taken from the baseline's foreign keys in S1, not from this spec. The polymorphic `aral_enrollments.basis_assessment_id` and `suggestion_assessment_id` are mapped through `crla_assessments` or `phil_iri_assessments` according to `basis_source` (the suggestion's source column).
    - update / delete: requires `row_version = base_version`; otherwise a conflict entry is collected and the walk continues so all conflicts are listed.
  - Any conflict → the sub-block is rolled back, status `conflict` with the list.
  - Any other error (RLS, CHECK, trigger) → rolled back, status `error`, `reason` = the message (with the record's table and key).
  - Success → status `applied`, `id_map` set, `decided_at`/`decided_by`.
  - Status changes go through a small `SECURITY DEFINER` helper (`SET search_path = public`) that only performs these transitions.
- `aral_tutor_settings` has a uuid key, not an id: a local row with no pulled server row is an insert, otherwise an update with its base version; an insert that hits an existing server row is an `error`.

### 2.4 Settings

Two new keys in `report_settings.settings` (per school, `school_id` null = region-wide row; already mirrored by pull), with CHECKs in the migration like `done_threshold`:
- `sync_auto_approve`: boolean, default false.
- `offline_signin_days`: integer 1-60, default 14.

## 3. Device (SQLite v34)

### 3.1 Record states

- **New:** `origin = 'local'`, **negative id**. Repositories assign it from a single countdown in `sync_meta` (SQLite triggers cannot rewrite `NEW.id`). Children carry the parent's negative id.
- **Pulled:** `origin = 'cloud'`, positive id, `row_version` from the server.
- **Edited / deleted pulled row:** `AFTER UPDATE` / `AFTER DELETE` triggers on each synced table (when the row's origin is `cloud`) write one line per record to `sync_changes (table_name, row_key, op, base_version)`, keeping the earliest base version; a delete replaces an update. No repository changes needed; this covers attendance marks, IRIP ratings and check-in answers on pulled records.
- **Deleting a new row** just removes it.

### 3.2 Pending lock

`sync_pending (table_name, row_key, upload_id)` lists every record in an upload awaiting a decision. `BEFORE UPDATE` / `BEFORE DELETE` triggers on the synced tables `RAISE(ABORT, 'pending upload')` for listed records; ViewModels turn it into "This record is waiting for approval. Withdraw the upload to change it."

### 3.3 Upgrade to v34

Adds `row_version`, `sync_changes`, `sync_pending`, the triggers, `offline_credentials` (section 6) and a `login_logs.mode` column; creators run unconditionally (`IF NOT EXISTS`, triggers dropped and recreated), never only inside `if (oldVersion < 34)`. One-time step: existing `origin = 'local'` rows are renumbered to negative ids together with their children, in one transaction.

## 4. Package

Built by `SyncViewModel` (pure Dart, own `ScopedLogger`):

```
{ "format": 1, "release": "<latest id in release.dart>", "device_id": "<uuid>",
  "records": [
    { "table": "aral_sessions", "op": "insert", "key": {"id": -5}, "row": {...} },
    { "table": "aral_attendance", "op": "update", "key": {"id": 812},
      "base_version": 3, "row": {...} },
    { "table": "aral_attendance", "op": "delete", "key": {"id": 813}, "base_version": 1 } ] }
```

- Contents: every unsent new record, plus every `sync_changes` line not already pending.
- Order: parents before children (the `_pullOrder` order).
- Children of a new parent are always included with it.
- Local-only columns (`origin`) are stripped; values converted back (SQLite 0/1 → bool, JSON text → jsonb).
- `summary` counts per kind and section are computed alongside.

## 5. Flows

### 5.1 Tutor (`SyncViewModel`, needs `requireOnlineSession()`)

1. `preview()` builds the package without sending it and fetches the server's `row_version` for every edited or deleted pulled record (one select per table). Returns counts per kind and section plus conflicts found early.
2. `resolve(table, key, keepMine | keepServer)`: keepMine moves the base version up to the server's current one (a knowing overwrite); keepServer drops the local change and refreshes that row from the server.
3. `upload()` inserts the `sync_uploads` row; only after the insert is confirmed are its records written to `sync_pending`. If the school has auto-approve on or the uploader is an admin/coordinator, it calls `sync_apply` at once.
4. `refreshStatus()` (every sync and online sign-in) reads the uploader's uploads and acts:
   - applied: replace negative ids with real ones via `id_map` (children too), re-read those records from the server, set `origin = 'cloud'` and `row_version`, clear their `sync_changes` and `sync_pending` lines. One local transaction; safe to repeat.
   - rejected / error: lift the lock; records editable again with the reason shown; they go in the next sync.
   - conflict: lift the lock, show the conflicts; resolve with `resolve()`.
   - withdrawn: lift the lock.
5. `withdraw(id)`: only while pending; lifts the lock.
6. `sync()`: `refreshStatus()` → `preview()` → (confirm) `upload()` → `pull()`. For the future UI button.

### 5.2 Approver (`SyncReviewViewModel`; admin, coordinator, superadmin; online)

- `pending({schoolId})`: `pending` and `conflict` uploads with uploader, date and summary, plus the "N uploads still pending" total.
- `details(id)`: the payload as plain lines ("Juan Dela Cruz, CRLA BOSY, Grade 2: new"; "Session 14 attendance: 2 marks changed"), names from the local copy.
- `approve(id)`: calls `sync_apply`. A conflict at this point goes back to the uploader (only their device has the data).
- `reject(id, reason)`: reason required.
- `setAutoApprove(schoolId, on)` and the offline window: through `ReportSettingsViewModel`, like the done threshold.

### 5.3 Console (one action per command, `core/console/commands/sync_commands.dart`)

Tutor: `sync-preview`, `sync-resolve <table> <id> mine|server`, `sync-upload yes`, `sync-status`, `sync-withdraw <id>`.
Approver: `sync-pending [school]`, `sync-show <id>`, `sync-approve <id>`, `sync-reject <id> <reason...>`, `sync-auto-approve [school] on|off`, `offline-days [school]`, `offline-days-set [school] <n>`.
Auth: `sign-in-offline <email> <password>`.
Wired into both `console/main.dart` and `main.dart`.

## 6. Offline sign-in

- After a successful online sign-in (active, version check passed, no pending password change), the device stores in `offline_credentials` (one row, the device owner): `user_id`, `email`, `salt` (16 random bytes), `iterations`, `hash` = PBKDF2-HMAC-SHA256(password), `last_online_at`, `failed_attempts = 0`. A new owner (section 7) overwrites it; `change-password` updates it.
- New dependency: `crypto` (dart-lang, pure Dart). PBKDF2 is a small function in `lib/core/services/`, tested against published SHA-256 vectors. The iteration count is a constant, tuned during the build to about 0.5 s on a low-end phone.
- `AuthViewModel.signInOffline(email, password)` succeeds only if: the email is the stored owner's; the hash matches; `now - last_online_at <= offline_signin_days` (school → region-wide → 14, from the local `report_settings` mirror); the local `users` row is active; `failed_attempts < 5` (five wrong passwords disable offline sign-in until the next online sign-in). Every attempt goes to the local `login_logs` with `mode = 'offline'`.
- Offline session: `currentUser` from the local users mirror, no `client`. Guards: `requireActiveSession()` = signed in, online or offline (local-copy work); new `requireOnlineSession()` = live server session (admin/content writes, imports, sync, pull, user management, `version-check`). The build audits every `authVm.client!` use so none can crash offline.
- Offline sign-in trusts the release recorded at the last online sign-in and the device clock.

## 7. Pull becomes a merge

The logic moves from `pull_commands.dart` into `SyncViewModel.pull()`; `pull-cloud` keeps its name and calls it. Download first (all the user can read, full), then one transaction:

| Group | Write |
|---|---|
| Not synced tables | replaced as today |
| Synced, pulled rows with no local edit | replaced by the server's copy, or removed if gone |
| Synced, pulled rows with a `sync_changes` line | local version kept; a moved-on or deleted server row surfaces as a conflict at the next preview |
| New rows (negative ids) | kept |
| Rows in a pending upload | kept, still locked |

- Orphans: a kept local row whose parent the server no longer gives this user → the pull refuses and lists those rows. `pull-cloud yes discard-local` remains the explicit way out (deletes new rows, journal and pending lines).
- Device owner = `sync_meta.last_pull_user`. A different user's online sign-in: if the owner has new, edited or pending work the switch is refused until they sync (or `discard-local`); otherwise warn, and the pull replaces everything as the new owner.

## 8. Updates while work is open

README *Keeping BASA up to date* gets a pre-update checklist for releases whose migration says `App update required on all devices: yes`: (1) every device syncs; (2) approvers decide every pending upload (none left `pending` or `conflict`; `sync-pending` shows the count); (3) only then apply the migration and update the devices. The migration header template and README 2b say the same in one line.

Safety net: the release guard refuses an old package instead of applying it under new rules; the records are still on the device (locked), so after updating the tutor withdraws the stale upload and syncs again.

## 9. Errors

- Upload response lost: `client_upload_id` lets a retry or `refreshStatus()` find the existing row; no duplicate.
- `sync_apply` response lost: status lives on the server; `refreshStatus()` reads it.
- Local id swap after `applied` fails partway: one transaction, pending lines remain, the next `refreshStatus()` redoes it.
- Package larger than the server's request limit (measured during the build): refused with "too much unsynced work; sync more often" and a per-kind breakdown.
- Offline / server unreachable: every sync step fails cleanly with nothing changed.
- Server errors (RLS refusal, CHECK, release guard) are mapped to plain messages in the ViewModels, as today.

## 10. Known risks

- A lost device keeps the offline credential and the local data. Deactivating the account or changing the password cannot reach an offline device; the old password works offline there until the window expires. The hash is salted and slow; the local DB is not encrypted (SQLCipher possible later).
- The offline window uses the device clock, which a user can change.
- Full pull on every sync; fine for a tutor's scope, slow for a superadmin's region.
