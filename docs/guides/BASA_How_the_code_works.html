BASA (ARAL-Read)
How the Code Works

A walkthrough of the system's parts and how they fit together

BASA is a reading-assessment app for tutors and reading coordinators in DepEd's ARAL-Reading program. It records CRLA (Grades 1 to 3) and Phil-IRI (Grades 4 to 10) assessments, runs ARAL tutoring classes, and produces the reports a school sends to the Division and the NLA portal.

This document explains how the code is built. It covers the layers, how data moves from a tutor's device to the server, how access is controlled, and how the release is checked. It is a summary; each part has a detailed design document in the repository (docs/superpowers/specs/).

1. The system at a glance

BASA has three kinds of parts: the apps on tutors' and coordinators' devices, a local database on each device, and one central server for a region or school.

Figure 1. Every device keeps its own copy of the data and exchanges it with one server.

Main choices

  • Offline-first. Schools often have weak or no internet. A tutor downloads the data once, then works from the copy on the device. Finished work is sent to the server later in one upload.
  • Low-cost server. Supabase (PostgreSQL) runs in the cloud or on a cheap computer on the school's network. The same app talks to either one; only the address changes. No files are stored on the server; learning materials are linked from Google Drive.
  • The database protects the data. Access rules are written in the database itself (row-level security). The app cannot show a tutor data the server would not give them, even if the app had a bug.
  • Two apps. A tutor app and an admin app (coordinators and admins) are built from the same code. The tutor app does not contain admin features at all.

2. Layered design (MVVM)

The code follows Model–View–ViewModel. Each layer has one job and may only call the layer below it. Every module (CRLA, Phil-IRI, ARAL, …) is built in the same order, from the bottom up.

Figure 2. Arrows point to what a layer may call.
LayerWhat it does
ModelsPlain Dart classes such as Student, CrlaAssessment and AralClass. Each one turns itself to and from a database row. They hold no logic beyond that.
Repository interfacesAbstract lists of operations, e.g. "get the learners of a section". The rest of the app depends only on these, not on a particular database.
SQLite / Supabase versionsTwo implementations of each interface: one reads and writes the device copy, the other the server. Because both follow the same interface, a ViewModel works the same online and offline.
ServicesPure rules with no database access: CRLA and Phil-IRI scoring, ARAL program placement, the SF1 and workbook readers, the Excel writers. They are easy to test because they only take values and return values.
ViewModelsThe app's logic. A ViewModel checks who is signed in and what they may do, validates the input, calls the repositories and services, and turns errors into short messages a tutor can understand. ViewModels never import Flutter, so they also run in the plain-Dart console.
Views (screens)Flutter widgets. A screen only calls ViewModels. It never touches a repository or the database.
The boundaries are enforced by tools, not only by agreement. tool/check_vm_boundary.dart fails if a screen or console command imports anything except ViewModels and models. It runs after every change and in every release build.

3. How the app starts and connects its parts

All four entry points build the same objects in the same way: the admin app, the tutor app, and the admin and tutor developer consoles. This "wiring" lives in lib/core/wiring/.

  1. Data folder. Each build keeps its files in its own folder (Documents/BASA/admin or …/tutor): the SQLite database, the server address and the colour settings.
  2. AppContext.open opens the SQLite database and creates or upgrades its tables to the current schema version. It also loads the server settings and creates the AuthViewModel, which handles sign-in.
  3. wireShared → wireTutor → wireAdmin create every repository and ViewModel and connect them. The tutor app stops after wireTutor; only the admin app calls wireAdmin.
  4. The ViewModels are collected into one object (AppViewModels; the admin app also has AdminViewModels). BasaScope places it at the top of the screen tree, so any screen can write BasaScope.of(context).crla to reach the CRLA ViewModel.
  5. In debug builds, the same ViewModels are also registered as console commands. Developers can then run every feature by typing, without opening a screen.
Figure 3. Start-up, from entry point to screens.

ViewModels are request and response

A screen calls a ViewModel method and waits for the answer, for example await vms.crla.getResult(id). A ViewModel does not hold screen state or push updates to the screen. This keeps the ViewModels simple and lets the console call exactly the same methods as the screens.

The developer console

lib/console/main.dart (admin) and main_tutor.dart (tutor) run in plain Dart, without Flutter. Each command performs one action through a ViewModel, e.g. crla-result or sync-upload. Every feature was built and tested here first and only then given a screen. Shipped release builds do not contain the console.

4. The data model

The server runs PostgreSQL. Each device has a SQLite database with the same table names, so the same rows can move between the two. Columns use snake_case.

GroupMain tablesPurpose
Coreregions, schools, sections, students, enrollments, users, tutor_section_assignmentsSchools and their sections per school year. Learners are identified by their LRN; an enrollment puts a learner in a section for one year. Many schools share one regional database.
CRLAcrla_assessments, crla_part1_*, crla_part2_fluency, crla_storiesOne assessment per learner, language and attempt, plus its Part 1 and Part 2 scores. Views compute each result and the section and school summaries.

Planning and reportsassessment_calendar, report_settings, aral_settings, srp_classesRound dates per region with school overrides, school-level settings (e.g. the "done" threshold), and summer remediation classes.

How the schema changes

  • supabase/migrations/20261018040000_baseline.sql holds the whole server schema. Every later change is a new migration file, and the baseline is never edited.
  • Every migration states whether it requires all devices to update the app. It also records itself in the basa_migrations table, which the version check reads (section 10).
  • On the device, local_database.dart creates the SQLite tables and upgrades them step by step to version 45. It also holds the SQLite triggers that refuse invalid rows, for example a CRLA assessment for a Grade 5 section.

Rules in more than one place, on purpose

Important rules are checked in three places: the ViewModel (to give a clear message), the SQLite trigger (to protect the device copy), and the server's policies or functions (the final authority). For example, an ARAL class cannot hold more than 15 active learners. The ViewModel refuses the 16th with a plain message, and the server refuses it even if an old app version sends it.

5. Who can see what: roles and row-level security

RoleCan see and changeApp
Superadmin
(admin without a school)		Every school in the region; regional settings and content.Admin app
Admin / coordinatorEverything in their own school. The two roles have the same rights.Admin app
TutorOnly the sections assigned to them and the learners of the ARAL classes they teach. They assess those learners and run their classes.Tutor app

Row-level security (RLS)

PostgreSQL decides, row by row, what each signed-in user may read or write. Every table has policies built from a few helper functions in the database:

  • is_superadmin(): regional access;
  • own-school checks for admins and coordinators;
  • tutor_has_section() and tutor_has_student(): a tutor's assigned sections and their learners, including the learners of the ARAL classes they teach.

The app only ever uses the public "anon" key and the user's own sign-in. It never holds a key that bypasses these rules. Creating an account needs more rights, so it goes through a small Edge Function on the server (create-user), which checks the caller's role first.

Every view is created with security_invoker = true. A view then applies the RLS of the person asking; otherwise it would show every row. Tests check that each new table grants access to signed-in users only, never to anonymous visitors.

Actions that change many rows go through server functions

Some actions must happen completely or not at all. Examples: applying a sync upload, archiving a learner who left, moving a learner to another section. Each is a single SECURITY DEFINER function on the server that checks the caller's role and runs in one transaction. Only these functions may change a learner's section.

Sign-in

  • The first sign-in on a device must be online, through Supabase Auth. New accounts get a temporary password that must be changed.
  • After that, the device owner (the last person who downloaded data on it) may sign in offline for a limited number of days (14 unless the school changes it). The device stores only a salted PBKDF2-SHA256 hash of the password for this.
  • Anything that needs the server, like sending work or downloading, requires a live online sign-in.
  • Every sign-in attempt is logged on the device and on the server.

6. Working offline and syncing

Sync is the most complex part of BASA. The aim: a tutor can work for days without internet, and the server still never takes in work that nobody checked or that clashes with newer data.

Figure 4. The sync cycle.

How it works

  • Download is a merge, not a wipe. Rows the user has not changed are replaced with the server's copy. New, edited and pending rows are kept. If kept rows point to records the server no longer gives this user, the download stops and explains why, so nothing is left orphaned.
  • New rows get negative ids on the device, e.g. -3. The server gives the real ids when the upload is applied, and the device then replaces its temporary ids everywhere.
  • Edits are recorded in a journal, together with the server version they started from. That is how the server detects a conflict: someone else changed the same row after the tutor's download. The tutor chooses Keep mine or Take the server's. Nothing is overwritten silently.
  • One upload, one decision. All unsent work goes to the server as a single package (sync_uploads). Until it is decided, those records are read-only on the device. A coordinator reviews and approves it; uploads by coordinators, or at schools with automatic approval, are applied at once.
  • All or nothing. The server function sync_apply applies the whole package in one transaction. If any row fails a rule, nothing is applied and the reason is reported.

One device, one owner

The device copy belongs to one user, the last person who downloaded. When another person signs in online, the copy is cleared first, so they never see the previous user's data. While the owner still has unsent work, other people cannot sign in on that device until the owner sends it. This protects learners' data on shared school devices.

Plain messages

Sync results are shown in plain English and name the learner, e.g. "The Phil-IRI session of Juan Dela Cruz was changed on the server". They never show table names, ids or console commands. An automated test (console_wording_test) checks this, because many tutors and coordinators read English as a second language.

7. The modules: CRLA, Phil-IRI, ARAL

They were built in a fixed order: CRLA, then Phil-IRI, then ARAL. ARAL uses the results of the other two.

CRLA (Grades 1 to 3)

  • A tutor records an attempt for a learner in Mother Tongue, Filipino or English. Part 1 holds the letter and word tasks; Part 2 is a story read aloud, with comprehension questions.
  • The scores are computed in the database. SQLite triggers on the device and SQL views on the server work out words per minute, totals and the reading profile (Low Emerging … Reading at Grade Level). Both sides therefore give the same answer.
  • The cut-off scores are settings, not fixed numbers (CrlaThresholdViewModel), so a region can change them without a new app.
  • The scoresheet can be imported from, and exported into, the DepEd CRLA Excel template.

Phil-IRI (Grades 4 to 10, English)

  • Content: collections of graded passages with their questions, and rubric criteria, loaded from seed files.
  • Assessment: a group screening test (GST) for the class first, then one session per learner per round (BOSY, MOSY 1–3, EOSY). In a session the tutor records the miscues, the reading time and the answers for one or more passages. A learner never reads the same passage twice.
  • Scoring lives in phil_iri_rules.dart and phil_iri_results.dart. They compute the word-recognition, speed and comprehension levels (Independent … Non-Reader) and the adjusted reading level, following the coordinators' reference table. The cut-offs are adjustable settings.
  • Each round has a status: assessed, carried over or not assessed. Progress figures count only assessed rounds. Schools choose per report whether to show a learner's best result so far ("carried") or only that round's reading ("actual").
  • Results from a coordinator's existing Excel workbook can be imported. A preview shows what will change, and a confirmation code must be entered before anything is written.

ARAL-Reading (tutoring)

  • Roster: aral_rules.dart proposes the learners who need tutoring and their program (Foundational, KS1, KS2, KS3, Basic or Plus) from their latest CRLA or Phil-IRI result. Teachers can also refer learners.
  • Classes: a class holds at most 15 learners and has one tutor. Enrolling a learner and placing them in a class are two separate steps. Grade or program mismatches need the coordinator's confirmation.
  • Daily work: sessions with attendance (excused absences don't count against the rate); the weekly reading plan (IRIP) with ratings; check-in tests after sessions 16 and 32, with an adjustable pass mark.
  • Exits and updates: when new assessment results arrive, the roster suggests program changes or exits. Learning materials are recommended per program from a catalogue of Google Drive links.

8. Imports, exports, reports and the dashboard

Imports

  • SF1 (School Form 1), the official class register, creates sections, learners and enrollments. sf1_importer.dart reads .xls and .xlsx files, matches columns by their headers and runs a trial first. Learners already in BASA are matched by LRN. Rows that clash with existing data become import conflicts for a person to decide.
  • Learners who left: re-importing an SF1 lists learners no longer on it. The coordinator can archive them (records kept), move them to another section, or restore them. After a set period an archived learner may be anonymized, but only on request with a confirmation code, never automatically.
  • CRLA scoresheets and Phil-IRI workbooks are imported through the same preview-then-confirm pattern.

Exports and reports

Report builders are pure functions. They take the results and return rows; Excel and CSV writers then put those rows into DepEd's own template layouts.

ReportWhat it shows
NLA portal report (Form 2b)Phil-IRI results per category, ready to enter in DepEd's NLA portal.
ARAL implementation reportThe Division's ARAL report, in the template's layout.
Progress monitoringHow many learners of each section have been assessed in a round, against a "done" threshold (85% unless changed).
BOSY masterlistLearners not reading at grade level at the start of the year.
Summer Remediation (SRP)Ranked candidates, and classes with a tutor, room and schedule.
Phil-IRI rankingThe lowest learners of a round by accuracy, speed or comprehension, with a list of those who could not be ranked and why.
Learner historyOne learner's progress over the years (admin app only, for privacy).

Dashboard

  • Round calendar: assessment windows per region, with school overrides or skips.
  • Reminders: for coordinators (sections behind schedule) and for tutors (learners not yet assessed, check-ins due, classes with no recent session).
  • Trends: charts of reading levels, completion, CRLA profiles and ARAL exits.
  • Summary: one view per role: a tutor sees their own classes, a school its sections, the region every school.

The dashboard owns no rules of its own. It only reads results from the report and reminder ViewModels, so a number on the dashboard is always the same as in the matching report.

9. Two apps from one codebase

The admin app (lib/main.dart, "BASA") and the tutor app (lib/main_tutor.dart, "BASA Tutor") come from the same code. Each is built for Android and for Windows, with its own installer.

Why two apps?

The server's RLS already stops a tutor from doing admin work. Leaving admin code out of the tutor app goes further: a tutor's device does not contain the screens, messages or logic for user management, reports, imports or approvals. It is also smaller and simpler.

How the split is kept honest

  • Where the line is: a feature is "admin" if the server's rules would refuse it to a tutor. Admin-only ViewModels are created only in wire_admin.dart; admin-only console commands live in *_admin_commands.dart files.
  • Import walk (tool/check_tutor_imports.dart): follows every import from the tutor entry points. It fails, and shows the chain of imports, if the tutor build reaches an admin file.
  • Marker scan (tool/scan_markers.dart): some admin methods sit in ViewModels both apps share; the compiler removes them from the tutor build because no tutor screen calls them. To prove this, the release script searches the compiled apps for marker texts (for example admin-only refusal messages). Each [admin] marker must be in the admin build and in no tutor build.
  • No console in release builds: the developer console exists only in debug builds and in special "scan" builds that are used for checking and never shipped.

The release script

tool/build_release.ps1 builds everything and stops at the first failed check. In order:

  1. Fetch packages, and check that the patched local copies of third-party packages are used.
  2. Run the import walk and the ViewModel boundary check.
  3. Build both apps for Android and Windows, plus two scan builds.
  4. Run the marker scan, including a self-test that the scan really finds markers.
  5. Create the Windows installers. They include a user guide and a glossary written in plain English.

10. Keeping devices and server in step

Every device and the server must run the same BASA release. An old app writing to a newer database, or a new app working against an old one, could store wrong results. BASA prevents this at sign-in:

  • The app carries the list of migrations it was built for (lib/core/release.dart).
  • The server keeps a record of the migrations it has applied (basa_migrations). Each migration also says whether all apps must be updated.
  • At sign-in, version_check.dart compares the two lists. If the server is missing a migration the app needs, or has a required one the app doesn't know, sign-in is refused with an explanation. Smaller differences only show a warning.
  • Before a required update, every device sends its work and every upload is decided, so no work is stranded between versions.
