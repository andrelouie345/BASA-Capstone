# lib/core — data layer conventions

Nothing in `core/` imports Flutter. Keep it that way.

## Models (`models/`)
- Plain Dart classes. Nullable `id`, `toMap()` with snake_case keys (omit `id` when null), `factory fromMap(Map<String, Object?>)`. Dates are ISO strings.
- Part tables (`CrlaPart1Standard`, `CrlaPart1English`, `CrlaPart2Fluency`) have **no `id`**: `assessmentId` is both primary key and FK to `crla_assessments.id`, and is always included in `toMap()`.
- **Postgres generated columns are read-only.** `total_score` (both Part 1 tables) and `wpm` are `GENERATED ALWAYS`. They are read in `fromMap()` but never written in `toMap()`; writing them errors in Postgres. Part 1 `reading_level` stopped being generated in migration 20261015000000 (it depends on adjustable thresholds): `toMap()` sends it when known (locally `CrlaViewModel` computes it); the cloud's trigger overwrites it.
- `numeric` columns (`wpm`, `pct_correct_words_read`) can arrive as int or double: read as `(m['x'] as num?)?.toDouble()`.
- `CrlaResult` maps the `crla_results` view: read-only, no `toMap()`. `pctCorrectWordsRead` is a 0–1 fraction rounded to 4 places, not a percentage.
- Language normalization: `crla_language.dart` → `normalizeCrlaLanguage()` maps "Filipino" (case/space-insensitive) to "Tagalog". `CrlaAssessment.toMap()` writes `normalizedLanguage` (variant `fil` always stores "Tagalog"; otherwise the normalized string). `CrlaStory.toMap()` normalizes too, because stories will be imported from source files that say "Filipino". Normalization happens only on writes through `toMap()`; a raw SQL load can bypass it. Callers should use the row returned by `insert()`, not the in-memory object they passed in.

## Repositories
- Interface in `repositories/`, SQLite impl in `data/local/`, Supabase impl in `data/remote/`.
- `upsertWithId(...)` is for local mirroring only (keeps the cloud-generated id). Supabase impls throw `UnimplementedError`. SQLite impls (schools, sections, students, crla_stories, crla_assessments) go through `data/local/mirror_write.dart` → `upsertById()`: UPDATE by id, else plain INSERT. A unique-key clash under a different id (LRN, school code, section 4-tuple, attempt) throws `MirrorConflictException` instead of INSERT OR REPLACE silently deleting the other row. `pull-cloud` uses the same helper.
- Supabase `update()` pattern: remove the key from the payload, filter on it, call `.select()`, and throw if the result is empty (that is how an RLS rejection looks from the client).
- Supabase `insert()` returns the stored row via `.select()` so DB-assigned and DB-computed values (`attempt_no`, totals, wpm) come back.
- Repos don't catch `PostgrestException`; ViewModels and console commands decide how to report it.
- **Rounds (2026-10-15).** `crla_assessments.round` is `bosy`/`mosy`/`eosy` (`CrlaRound`; rows from before it exist are `bosy`; cloud migration `20261015040000_crla_round.sql`, local v18). `attempt_no` still counts across rounds (unique key and attempt triggers unchanged); a round's latest attempt is its highest `attempt_no`. `crla_latest_attempts` is latest **per round** and the three summary views are per round; every CRLA view has `round` as its last column. ARAL-Reading uses it (G1 enters on MOSY, G2-3 on BOSY).
- `crla_assessments` has **no update** on purpose: a retake is a new row. The cloud has no UPDATE policy for it (dropped in M4). Only the scoring is rewritten in place: by SECURITY DEFINER triggers / `crla_regenerate_results` in the cloud, and by the local-only `setReadingProfile` on the device.

## CRLA semantics
- `crla_assessments` snapshots `school_id` and `section_id` (not `enrollment_id`) so a transfer or re-import never rewrites a past assessment.
- `attempt_no` is assigned by the database and resets to 1 per (student, school, section, subject_variant, school_year). Never send it on insert. Postgres: `BEFORE INSERT` trigger `crla_assessments_before_insert` always assigns it (a client value is ignored). SQLite: column default 0 plus an `AFTER INSERT` trigger that fires only when `attempt_no = 0`, so mirrored rows keep the cloud's number. Because sqflite's `insert` returns only the rowid, **the SQLite repo must re-read the row** to get the assigned `attempt_no`.
- `subject_variant` ∈ `mt`, `fil`, `eng`. Standard Part 1 requires `mt`/`fil`; English Part 1 requires `eng`. Enforced in the DB by a variant-check trigger (Postgres: insert and update; SQLite: insert and update of `assessment_id`).
- Part 1 CHECKs (identical on both sides): standard — `task2_low_score` only when `task1_score < 7`, `task2_high_score` only when `task1_score >= 7`; English — `task2_score` must be NULL when `task1_score = 0`.
- Part 1 level thresholds (the defaults; adjustable, see below): standard (task1<7: total ≤10 Full, >10 Moderate; task1≥7: total=task1+10+task2_high, <27 Light, ≥27 Grade Ready); English (0 Full, 1–10 Moderate, 11–16 Light, 17–20 Grade Ready).
- Grade rules come from the CRLA2 G1–G3 scoresheets and depend on the **section's grade** (CRLA is Grades 1–3 only) and the variant: comprehension max G1 5, G2 6, G3 mt/fil 7, G3 eng 6; reading-time cap G1 60 s, G2 120 s, G3 mt/fil 180 s, G3 eng 120 s (enforced for compliance). Grade/variant pairs with no sheet (e.g. G1 eng) are parked and use their grade's row. Postgres: `crla_comprehension_max`, `crla_time_cap_seconds`, trigger `check_crla_part2_limits`. Dart: `core/services/crla_rules.dart` (used by `CrlaViewModel`). SQLite: triggers `check_crla_part2_limits_ins/_upd` and `check_crla_assessment_target` (grade 1-3 section of that school + active enrollment), which skip mirrored rows (insert with `wpm` / `attempt_no` already set). Change all four places together. These are instrument facts and stay fixed. `observation_level` is stored even though no formula uses it (deliberate).
- **Words read (2026-10-23, command pass F10, owner decision).** Part 2 words read = the story's words − miscues, exactly as the CRLA2 scoresheet computes it (column M; ENG stories are 100 words, the ENG sheet's 100 − miscues). Dart: `crlaWordsRead` in `crla_rules.dart`, used by `CrlaViewModel.savePart2Fluency` (a typed value is only accepted when it equals that, as a scoresheet row does, or when no story matches; more miscues than words is refused). Postgres: the same rule in `check_crla_part2_limits` (migration `20261023020000`, sets `words_read` BEFORE insert/update so the generated `wpm` and the profile triggers follow). No story for the region/language/grade/story number: the typed value is kept (`crla-part2 … words=<n>`). Rows stored before keep their value until next updated. No SQLite trigger: device entries always go through the ViewModel and pulled rows carry the server's value.
- **Adjustable thresholds (2026-10-15).** The Part 1 refresher bands and the reading-profile bands are `CrlaThresholds` in `crla_rules.dart` (defaults = the DepEd scoresheet formulas exactly, gaps included). Stored as a region row + per-school overrides in `crla_thresholds` (effective = defaults <- region <- school). Each `crla_assessments` row snapshots the effective thresholds when it is started (`thresholds_snapshot`); its Part 1 level and its `reading_profile` are computed from that snapshot and **stored**, so changing thresholds never rewrites old results. Re-scoring with today's thresholds is explicit: cloud `crla_regenerate_results(ids)` (superadmin, or admin/coordinator of the school). Cloud: triggers `crla_part1_*_set_level` and `crla_*_refresh_profile`, helpers `crla_threshold_defaults()` (must equal `CrlaThresholds.defaults.toMap()`), `crla_reading_profile_t()`. Local: `CrlaViewModel` computes with `crla_rules.dart` and stores; the SQLite triggers compute `total_score`/`wpm` only. Mirrored rows keep the cloud's level/profile. The cloud stamps its own snapshot on insert (a client value is ignored).
- `reading_profile` replicates each grade's Excel formula (U11): Low Emerging from Full Refresher (and Moderate in G1 only), then per-grade comprehension cut-offs; NULL until Part 1 exists. Quirks kept on purpose (e.g. 0.50 < pct < 0.51 with enough answers yields NULL, as in the Excel). Do not "fix" them without asking. Summary views divide comprehension by the grade max and leave Full Refresher learners out of the fluency/comprehension/wpm averages.
- `crla_results` returns every attempt. Latest-only logic lives in `crla_latest_attempts` (and the two summary views built on it).

## SQLite (`data/local/local_database.dart`)
- Version-numbered schema (v38 as of 2026-10-24 — check the file; v34 = sync bookkeeping, below; v35 = `aral_enrollments` rebuilt for the `classroom_support` exit reason by `rebuildAralEnrollmentsForV35`, which copies every column of the old table, `row_version` included, and runs before every creator in onUpgrade because it drops the triggers and views that mention the table; v36 = ARAL classes: `aral_classes` + `aral_enrollments` rebuilt the same way with `class_id` and the referral columns, without `tutor_id` (`rebuildAralEnrollmentsForV36`, right after v35 and before v21); v37 = `aral_sessions.class_id` added with `ALTER TABLE ... ADD COLUMN ... REFERENCES` (no rebuild needed: nothing else changes) and `aral_tutor_settings` dropped (`upgradeAralSessionsForV37`); v38 = `aral_classes` rebuilt without `grade_band`, with `grade_level` (the lowest grade of the old band) and a nullable `program` (`rebuildAralClassesForV38`, copies every other column, `row_version` included, runs before every creator). A device reference to a synced table must be a declared `REFERENCES`: `followLocalIds` and the pull's orphan check find it with `PRAGMA foreign_key_list`). v14 added the `crla_thresholds` mirror, `crla_assessments.thresholds_snapshot` / `reading_profile`, made the Part 1 compute triggers total-only (DROP + CREATE), and backfills older rows with the default snapshot and their profile (`backfillCrlaScoring`). Its column adds run before the CRLA creators because `crla_results` reads `reading_profile`. v13 added the Phil-IRI tables, built by `phil_iri_local_schema.dart` (`createPhilIriLocalSchema`, called from onCreate and unconditionally from onUpgrade). Phil-IRI content tables are mirror-only locally (no triggers); `phil_iri_gst_results` and `phil_iri_assessments` carry the same local-only `origin` column as `crla_assessments`, and the local triggers re-check the cloud's rules only for `origin = 'local'` rows and their children. v12 added the local-only `crla_assessments.origin` ('local' = entered on this device, not uploaded; 'cloud' = mirrored; existing rows upgrade as 'local') and the `sync_meta` key/value table used by `pull-cloud`. The cloud has no `origin` column, so it is never in `CrlaAssessment.toMap()`; the SQLite `upsertWithId` and `pull-cloud` set it to 'cloud'. v11 rebuilt `crla_part2_fluency` to widen the comprehension CHECK to 0..7 (`_rebuildCrlaPart2ForV11`, runs before the CRLA creators). `onCreate` builds everything; `onUpgrade` re-runs the CRLA creators unconditionally at the end (all `IF NOT EXISTS`), after the schools rebuild, so new CRLA objects appear on upgrade. **Do not put new-table creators inside `if (oldVersion < N)` blocks that existing installs skip.** Bump the version when adding anything.
- Order matters: regions → students/schools/sections/enrollments → users → CRLA tables (they reference schools, students, sections, users).
- SQLite can't do `BEFORE INSERT` row rewrites, hence the attempt_no pattern above. Generated columns are avoided (need SQLite ≥ 3.31, which older Android lacks): totals, reading levels and wpm are computed by `AFTER INSERT` / `AFTER UPDATE OF <score cols>` triggers that write only the computed columns, so they cannot loop.
- The fluency insert trigger runs only `WHEN NEW.wpm IS NULL`, so rows mirrored from the cloud keep the cloud's wpm. Postgres and SQLite can differ by 0.1 at rounding boundaries; the cloud value wins. The CRLA Part 1/2 tables (and `enrollments`, one per learner per year) are still mirrored with `INSERT OR REPLACE`: their primary key is their only unique key, and an UPDATE would re-run the compute triggers over the cloud's wpm/totals. Since v14 the Part 1 triggers no longer touch `reading_level`, so a mirrored row keeps the cloud's level. Mirrored `crla_assessments` keep their id, `attempt_no`, snapshot and profile.
- **Local foreign keys are off on purpose** (`PRAGMA foreign_keys` is never enabled). The local DB is a role-scoped partial copy: e.g. `users.created_by` and `crla_assessments.administered_by` can point at users the signed-in account can't read, so enforcing FKs would break `pull-cloud`. The cloud enforces them. Never write mirrors with INSERT OR REPLACE on tables with secondary UNIQUE keys or child rows.
- `crla_results` also exists as a SQLite view with the same column names as the Postgres one; both read the stored `reading_profile`.
- Anything changed here must keep local and cloud behavior symmetric (offline and cloud attempt numbering, CHECKs and triggers must agree).
- **ARAL Key Stage 1 (DepEd Memorandum 064 s. 2025, owner 2026-10-23; cloud `20261023030000`).** Rules in `aral_rules.dart`: `aralCrlaQualifies(profile, extended:)` (Low/High Emerging; Developing/Transitioning only when the school's `ks1_extended` switch is on, `AralProgramSettings.ks1Extended`), `aralCrlaBasisVariant` (the CRLA that counts: G1 Mother Tongue else Filipino, G2 Filipino, G3 English; other languages are ignored). `AralViewModel.applyResults` exits a KS1 learner whose latest CRLA in that language is Developing/Transitioning with `classroom_support` (switch off), at any round; Reading at Grade Level stays `grade_level_ready`. The implementation report counts `classroom_support` under "other reasons". `aralCrlaLearnerProfile` (implementation report, dashboard CRLA trend) reads the same language (or the trend's explicit variant filter).

- **ARAL classes (spec `docs/superpowers/specs/2026-10-23-aral-classes-design.md`; cloud `20261023040000` + `20261024010000`, SQLite v36/v37/v38).** A learner sits in at most one class (`aral_enrollments.class_id`, null = waiting for a class); their tutor is the class's tutor (`AralEnrollmentRepository.classTutorId`; `getByTutor` goes through the class). A class has a home grade (`grade_level` 1-10, required) and one program or mixed programs (`program` null; `AralClass.isMixed`); a class with learners keeps both. An active learner going into a class (placement, a move, reactivation) must match the class's school and year and, in a one-program class, its program (`AralClassProgram.of(keyStage, track)`), and the class must have fewer than 15 other active learners. The same rule lives in three places, change them together: `aralPlacementProblem` in `services/aral_rules.dart` (the ViewModels refuse first with a readable sentence, `aralPlacementRefusal`, which returns the problem kind too), the local triggers in `aral_local_schema.dart` (rows made on the device: they check only `origin = 'local'` rows, so a pulled learner placed, moved or reactivated on the device is checked by the ViewModel there and by the cloud at upload), and the cloud's `aral_check_class_placement` (school, year, program) plus the constraint trigger `aral_enrollments_class_cap` (the 15 cap; since `20261024050000`). The cloud's two counting checks (`aral_enrollments_class_cap`, `aral_sessions_one_per_day`) are `DEFERRABLE INITIALLY IMMEDIATE`: direct writes are checked at once, and `sync_apply` defers them to the end of an upload (an upload carries final states, so an offline swap of places or dates can't pass record by record). A new counting rule across rows goes the same way. **Grade is checked only in the ViewModel** (`AralPlacementProblem.otherGrade`): a learner of another grade than the class's goes in only with the coordinator's confirmation (`aral-class-place … other-grade`); enrol with a class, enrol-proposed, referral and roster import leave them waiting with a warning. Neither the device triggers nor the cloud check grades. A program or grade change that keeps the learner in their class is not re-checked: the learner stays and is flagged (`aral-update`; coordinator reminders `AralClassNoticeKind.programMismatch` / `otherGrade`); a full or unsuitable class never blocks an enrolment (the learner waits, `lastWarning` says so). A referred learner (basis `referral`) exits only grade-level ready. A session belongs to a class: one per class per date, `session_no` per class, check-ins after a class's 16th/32nd session; sessions from before classes keep no class. A class is deleted only when no learner and no session points at it (`deleteClass`; the device doesn't enforce foreign keys, the cloud's would refuse the upload). A tutor marks attendance in a class session only for that class's learners (`mark`; cloud `check_aral_attendance` since `20261024040000`).

## Sync bookkeeping (SQLite v34; spec `docs/superpowers/specs/2026-10-20-sync-design.md`)
- The 18 synced tables (`syncedTables` in `data/pull_tables.dart`; `aral_classes` in and `aral_tutor_settings` out since v36/v37; triggers in `data/local/sync_local_schema.dart`) carry `row_version`: NULL = new on this device, not NULL = copy of a server row (0 = pulled before v34, version unknown).
- **Every new row in the 15 id-keyed synced tables gets `'id': await nextLocalId(db)`** (`sync_local_writes.dart`; -1, -2, ... one countdown, never reused). A trigger refuses a new row with a positive id. Lists that order by id use `(id < 0), abs(id)`.
- Edits/deletes of server rows are journaled in `sync_changes` by triggers; ops the server refuses are refused locally (`crla_assessments` and `phil_iri_gst_results` insert-only, except the CRLA `reading_profile`; CRLA parts never deleted). Rows in `sync_pending` (an upload awaiting a decision) can't change, and no child can be added under them (`pendingLockMessage`: "This record is waiting for approval. Withdraw the upload to change it.").
- Cloud rows copied down outside a pull go through `mirrorSyncedRow` (not `upsertById`); the pull runs under `withSyncBypass`. The bypass only exists inside a transaction.
- A table rebuild must copy `row_version` and run before `createSyncLocalSchema` (called last), which recreates the sync triggers.
- A new synced table, or a new boolean/jsonb column on one, must be added to `syncedTables` / `pullOrder` in `data/pull_tables.dart` and to the lists in `services/sync_upload_rules.dart` (they convert SQLite 0/1 and JSON text to the server's types), plus `row_version` on the server and a `sync_apply` change (migration, app update yes).

## Sync flow (S4-S6; `SyncViewModel`, `SyncReviewViewModel`)
- **Pull** (`SyncViewModel.pull`, console `pull-cloud`) is a merge: full download first, then one transaction (`SyncLocalRepository`). Device owner = `sync_meta` last pull user; uploads, `refreshStatus` and offline sign-in are the owner's only.
- **Package** (`upload_local` / `sync_upload_local_sqlite.dart`): one upload = every journaled and new record, ordered deletes (children first), inserts (parents first, negative ids in creation order), updates (children first). Each update/delete carries the `row_version` it was based on. **Follow-up updates** (migration 20261021010000): the server's insert triggers reset a new Phil-IRI session to in_progress and a new ARAL enrollment to active, so a record completed/finalized/exited offline travels again as an update with no base version right after its insert (`followUpsForNew`, `splitServerUpdate`). Limit `maxPackageBytes`.
- Locks are written **before** sending (with an in-flight marker) so nothing changes while the upload is on the way; `client_upload_id` makes a retry find the existing row instead of sending a duplicate.
- **`refreshStatus()`** runs at the start of preview/upload/pull: applied = take in (`id_map` swaps negative ids for real ones, children too, re-read from the server, journal and lock lines cleared); rejected/withdrawn/error = lock lifted; **conflict = the device withdraws the upload on the server first, then lifts the lock** (on failure the lock stays and the next refresh retries), so none stay in conflict.
- **Server**: `sync_apply(upload_id)` is security invoker and **writes as the uploader** (RLS and CHECKs are the uploader's; `created_by` = uploader, `decided_by` = approver). Release guard: a package made before a later migration marked app update required, or by a release the server doesn't know, is refused and stays pending (the tutor updates, withdraws it, syncs again; the approver can also reject it).
- **Approver** (`SyncReviewViewModel`, online): `pending` (own school; superadmin all or one), `details` = plain lines from `services/sync_review_lines.dart` (one line per owner record, children folded, names from the approver's local copy, ids when missing), `approve` (never changes the approver's device: pull to see the result), `reject` (reason required, at most 500 characters). Auto-approve and the offline window go through `ReportSettingsViewModel` (`report_settings` keys `sync_auto_approve`, `offline_signin_days`).

## ViewModel sign-in checks (command pass F5, 2026-10-23)
- Every public ViewModel method checks the sign-in itself, first: `requireActiveSession()` (online or offline sign-in) for work on the device's copy, `requireOnlineSession()` for anything that needs the server. Screens call ViewModels directly, so a check in the console command is not enough (CRLA was guarded only there; Phil-IRI not at all, and a signed-out device could start, score and discard sessions).
- `PhilIriViewModel`, `CrlaViewModel` and the seven ARAL ViewModels (`Aral`, `AralClass`, `AralSession`, `AralIrip`, `AralCheckin`, `AralReadability`, `AralMaterial`) use a private `_requireSignIn()`; `test/viewmodels/session_guard_test.dart` calls every public method of them while signed out and expects exactly `notSignedInMessage`. Add a new method there when you add one to one of these ViewModels. Since F18 (2026-10-24) `RoundCalendarViewModel` and `ReportSettingsViewModel` guard their local reads the same way (their writes already needed an online session).
- A refusal for "nobody signed in" always uses `notSignedInMessage` (`Not signed in. Sign in first.`), never a hand-written text (F19), so screens have one message to match.
- Console `asof=`/date options use `strictDateArg` (`lib/core/console/date_args.dart`): `DateTime.tryParse` alone rolls 2026-02-30 over to March (F17; every ARAL date argument too since F22). An optional positional date is recognised by its shape (`looksLikeDateArg`) and refused with `notARealDateMessage` when it isn't a real date, so it is never read as the next argument (notes).

## Console commands and the two builds (tutor build split, 2026-10-22)
- Every command is registered from `wiring/` (`registerSharedCommands`, `registerTutorCommands`, `registerAdminCommands`, `registerDevCommands`); entry points never register commands themselves.
- Which build: a command a tutor can use (RLS lets a tutor do it AND its ViewModel method doesn't refuse tutors) goes in the module's `<x>_commands.dart` and is in both builds. Anything else goes in `<x>_admin_commands.dart` (`register<X>AdminCommands`), or in a wholly admin command file listed in `tool/check_tutor_imports.dart`. Check the ViewModel method, not just RLS: `aral-export-roster`, `list-tutor-sections` and `aral-recommend-section` slipped into the tutor build once because their methods refuse tutors.
- A helper both halves need goes in `<x>_command_helpers.dart` with a module prefix (`philIriInt`, `PhilIriUsage`); never import an admin file from a tutor-side file.
- A new admin-only ViewModel, service or repository: add it to the list in `tool/check_tutor_imports.dart`, register it in `wire_admin.dart`, and add its ViewModel name to `[admin-release]` in `tool/admin_markers.txt`. A new admin-only method in a shared ViewModel: add one distinctive string from it (a refusal message or server function name, not a comment) to `[admin]`.
- ViewModel boundary (2026-10-24, spec `docs/superpowers/specs/2026-10-24-vm-completeness-design.md`): a command file imports only `viewmodels/`, `core/models/`, `core/console/` and the Dart SDK (`dart:io` is fine: a path is read into bytes here, ViewModels take bytes or strings). Never `core/services/`, `core/data/`, `core/wiring/`, `core/viewmodels/`, `core/release.dart` or a data package: what the command needs from a rule, repository or config becomes a ViewModel method or a model getter (that calls the same rule function), because a screen needs it too. A type defined in a service file is re-exported from a `core/models/` file (`export '../services/x.dart' show T;`). Dev-only files `test_data_commands.dart`, `debug_commands.dart`, `text_commands.dart` are exempt. `lib/ui/` follows the same rule (plus `ui/`, Flutter and UI packages; never supabase/sqflite/sqlite3; `ui/debug/` may use `core/console/`). `dart run tool/check_vm_boundary.dart` checks it; `tool/vm_boundary_baseline.txt` holds the violations left from before the rule and only shrinks.
- `ConsoleRegistry.register` throws on a name registered twice, so a command left in both halves fails at start-up and in the command-set tests.
- After the change: `flutter test` (command sets pin both builds: update `test/core/wiring/admin_commands.txt` / `tutor_commands.txt` on purpose) and `dart run tool/check_tutor_imports.dart` and `dart run tool/check_vm_boundary.dart`.

## Assessment rounds (one list per layer, changed together)
- An instrument's rounds live in: the Dart enums `PhilIriRound` / `CrlaRound` (`calendarRounds` in `services/calendar_rules.dart` is BUILT from them, never edited by hand); the cloud checks `phil_iri_assessments_round_check` / `crla_assessments_round_check`; and the calendar pairing `assessment_calendar_round_pairing` (migration 20261019050000), which must list exactly the same rounds.
- **Changing an instrument's rounds = the enum + ONE migration** that swaps the assessment table's round check and the calendar pairing together, converting (or deleting, owner's call) existing `assessment_calendar` rows first; the migration must refuse while unconverted rows exist (as 20261019050000 does), never delete silently. Every place that holds round names:
  - cloud: `phil_iri_assessments_round_check`, `crla_assessments_round_check`, `assessment_calendar_round_check` (names only, 20261019030000) + `assessment_calendar_round_pairing`, `aral_enrollments_basis_round_check` / `_suggestion_round_check`;
  - local SQLite: `phil_iri_local_schema.dart` (phil_iri_assessments.round), `local_database.dart` (crla_assessments.round, two places), `calendar_local_schema.dart` (round names), `aral_local_schema.dart` (basis_round, suggestion_round) — a CHECK change there needs a table rebuild and a version bump;
  - Dart: the enums; console argument lists in `crla_commands.dart`, `crla_import_commands.dart`.
- **Ship the app update before (or with) the migration.** An older app cannot pull data in a round it doesn't know: its local round CHECKs (assessment tables; the calendar's name list for a brand-new name) roll the whole `pull-cloud` back (nothing lost, cryptic error). The version check at sign-in (`services/version_check.dart`) refuses a device whose app is older than a migration marked app update required, but every device must still update.
- The local `assessment_calendar` has NO pairing check on purpose (exception to "CHECKs agree"): it buys only the narrow case of an existing round name re-paired before any assessment uses it, and avoids a third failure point. Rows the app doesn't know are ignored on read (`RoundCalendarViewModel.effectiveCalendar`), listed as INVALID by `calendar-show` (`invalidWindows`; mainly an updated app holding an old local copy until its next pull), and `pull-cloud` warns when it gets them.

## Supabase specifics
- `crla_assessments.administered_by` is a `users.id` (uuid, handled as a String). ViewModels set it from the signed-in user (for the local DB); the cloud overwrites it with `auth.uid()` in `crla_assessments_before_insert`.
- Cloud INSERT into `crla_assessments` requires `sections.school_id = school_id` and an **active** enrollment of the learner in that section for that `school_year` (any role), on top of the role scope.
- Postgres `date` columns come back as ISO strings; `birth_date` and `assessed_at` are `String` in models. `CrlaViewModel` writes `assessed_at` as the local calendar date (yyyy-MM-dd), never a UTC timestamp.
