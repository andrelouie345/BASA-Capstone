# lib/core — data layer conventions

Nothing in `core/` imports Flutter. Keep it that way.

## Models (`models/`)
- Plain Dart classes. Nullable `id`, `toMap()` with snake_case keys (omit `id` when null), `factory fromMap(Map<String, Object?>)`. Dates are ISO strings.
- Part tables (`CrlaPart1Standard`, `CrlaPart1English`, `CrlaPart2Fluency`) have **no `id`**: `assessmentId` is both primary key and FK to `crla_assessments.id`, and is always included in `toMap()`.
- **Postgres generated columns are read-only.** `total_score` (both Part 1 tables) and `wpm` are `GENERATED ALWAYS`. They are read in `fromMap()` but never written in `toMap()`; writing them errors in Postgres. Part 1 `reading_level` stopped being generated in migration 20261015000000 (it depends on adjustable thresholds): `toMap()` sends it when known (locally `CrlaViewModel` computes it); the cloud's trigger overwrites it.
- `numeric` columns (`wpm`, `pct_correct_words_read`) can arrive as int or double: read as `(m['x'] as num?)?.toDouble()`.
- `CrlaResult` maps the `crla_results` view: read-only, no `toMap()`. `pctCorrectWordsRead` is a 0–1 fraction rounded to 4 places, not a percentage.
- Language normalization: `crla_language.dart` → `normalizeCrlaLanguage()` maps "Filipino" (case/space-insensitive) to "Tagalog". `CrlaAssessment.toMap()` writes `normalizedLanguage` (variant `fil` always stores "Tagalog"; otherwise the normalized string). `CrlaStory.toMap()` normalizes too, because stories will be imported from source files that say "Filipino". Normalization happens only on writes through `toMap()`; a raw SQL load can bypass it. Callers should use the row returned by `insert()`, not the in-memory object they passed in.

## Repositories
- Interface in `repositories/`, SQLite impl in `data/local/`, Supabase impl in `data/remote/`.
- `upsertWithId(...)` is for local mirroring only (keeps the cloud-generated id). Supabase impls throw `UnimplementedError`. SQLite impls (schools, sections, students, crla_stories, crla_assessments) go through `data/local/mirror_write.dart` → `upsertById()`: UPDATE by id, else plain INSERT. A unique-key clash under a different id (LRN, school code, section 4-tuple, attempt) throws `MirrorConflictException` instead of INSERT OR REPLACE silently deleting the other row. `pull-cloud` uses the same helper.
- Supabase `update()` pattern: remove the key from the payload, filter on it, call `.select()`, and throw if the result is empty (that is how an RLS rejection looks from the client).
- Supabase `insert()` returns the stored row via `.select()` so DB-assigned and DB-computed values (`attempt_no`, totals, wpm) come back.
- Repos don't catch `PostgrestException`; ViewModels and console commands decide how to report it.
- **Rounds (2026-10-15).** `crla_assessments.round` is `bosy`/`mosy`/`eosy` (`CrlaRound`; rows from before it exist are `bosy`; cloud migration `20261015040000_crla_round.sql`, local v18). `attempt_no` still counts across rounds (unique key and attempt triggers unchanged); a round's latest attempt is its highest `attempt_no`. `crla_latest_attempts` is latest **per round** and the three summary views are per round; every CRLA view has `round` as its last column. ARAL-Reading uses it (G1 enters on MOSY, G2-3 on BOSY).
- `crla_assessments` has **no update** on purpose: a retake is a new row. The cloud has no UPDATE policy for it (dropped in M4). Only the scoring is rewritten in place: by SECURITY DEFINER triggers / `crla_regenerate_results` in the cloud, and by the local-only `setReadingProfile` on the device.

## CRLA semantics
- `crla_assessments` snapshots `school_id` and `section_id` (not `enrollment_id`) so a transfer or re-import never rewrites a past assessment.
- `attempt_no` is assigned by the database and resets to 1 per (student, school, section, subject_variant, school_year). Never send it on insert. Postgres: `BEFORE INSERT` trigger `crla_assessments_before_insert` always assigns it (a client value is ignored). SQLite: column default 0 plus an `AFTER INSERT` trigger that fires only when `attempt_no = 0`, so mirrored rows keep the cloud's number. Because sqflite's `insert` returns only the rowid, **the SQLite repo must re-read the row** to get the assigned `attempt_no`.
- `subject_variant` ∈ `mt`, `fil`, `eng`. Standard Part 1 requires `mt`/`fil`; English Part 1 requires `eng`. Enforced in the DB by a variant-check trigger (Postgres: insert and update; SQLite: insert and update of `assessment_id`).
- Part 1 CHECKs (identical on both sides): standard — `task2_low_score` only when `task1_score < 7`, `task2_high_score` only when `task1_score >= 7`; English — `task2_score` must be NULL when `task1_score = 0`.
- Part 1 level thresholds (the defaults; adjustable, see below): standard (task1<7: total ≤10 Full, >10 Moderate; task1≥7: total=task1+10+task2_high, <27 Light, ≥27 Grade Ready); English (0 Full, 1–10 Moderate, 11–16 Light, 17–20 Grade Ready).
- Grade rules come from the CRLA2 G1–G3 scoresheets and depend on the **section's grade** (CRLA is Grades 1–3 only) and the variant: comprehension max G1 5, G2 6, G3 mt/fil 7, G3 eng 6; reading-time cap G1 60 s, G2 120 s, G3 mt/fil 180 s, G3 eng 120 s (enforced for compliance). Grade/variant pairs with no sheet (e.g. G1 eng) are parked and use their grade's row. Postgres: `crla_comprehension_max`, `crla_time_cap_seconds`, trigger `check_crla_part2_limits`. Dart: `core/services/crla_rules.dart` (used by `CrlaViewModel`). SQLite: triggers `check_crla_part2_limits_ins/_upd` and `check_crla_assessment_target` (grade 1-3 section of that school + active enrollment), which skip mirrored rows (insert with `wpm` / `attempt_no` already set). Change all four places together. These are instrument facts and stay fixed. `observation_level` is stored even though no formula uses it (deliberate).
- **Adjustable thresholds (2026-10-15).** The Part 1 refresher bands and the reading-profile bands are `CrlaThresholds` in `crla_rules.dart` (defaults = the DepEd scoresheet formulas exactly, gaps included). Stored as a region row + per-school overrides in `crla_thresholds` (effective = defaults <- region <- school). Each `crla_assessments` row snapshots the effective thresholds when it is started (`thresholds_snapshot`); its Part 1 level and its `reading_profile` are computed from that snapshot and **stored**, so changing thresholds never rewrites old results. Re-scoring with today's thresholds is explicit: cloud `crla_regenerate_results(ids)` (superadmin, or admin/coordinator of the school). Cloud: triggers `crla_part1_*_set_level` and `crla_*_refresh_profile`, helpers `crla_threshold_defaults()` (must equal `CrlaThresholds.defaults.toMap()`), `crla_reading_profile_t()`. Local: `CrlaViewModel` computes with `crla_rules.dart` and stores; the SQLite triggers compute `total_score`/`wpm` only. Mirrored rows keep the cloud's level/profile. The cloud stamps its own snapshot on insert (a client value is ignored).
- `reading_profile` replicates each grade's Excel formula (U11): Low Emerging from Full Refresher (and Moderate in G1 only), then per-grade comprehension cut-offs; NULL until Part 1 exists. Quirks kept on purpose (e.g. 0.50 < pct < 0.51 with enough answers yields NULL, as in the Excel). Do not "fix" them without asking. Summary views divide comprehension by the grade max and leave Full Refresher learners out of the fluency/comprehension/wpm averages.
- `crla_results` returns every attempt. Latest-only logic lives in `crla_latest_attempts` (and the two summary views built on it).

## SQLite (`data/local/local_database.dart`)
- Version-numbered schema (v14 as of CRLA piece C3 — check the file). v14 added the `crla_thresholds` mirror, `crla_assessments.thresholds_snapshot` / `reading_profile`, made the Part 1 compute triggers total-only (DROP + CREATE), and backfills older rows with the default snapshot and their profile (`backfillCrlaScoring`). Its column adds run before the CRLA creators because `crla_results` reads `reading_profile`. v13 added the Phil-IRI tables, built by `phil_iri_local_schema.dart` (`createPhilIriLocalSchema`, called from onCreate and unconditionally from onUpgrade). Phil-IRI content tables are mirror-only locally (no triggers); `phil_iri_gst_results` and `phil_iri_assessments` carry the same local-only `origin` column as `crla_assessments`, and the local triggers re-check the cloud's rules only for `origin = 'local'` rows and their children. v12 added the local-only `crla_assessments.origin` ('local' = entered on this device, not uploaded; 'cloud' = mirrored; existing rows upgrade as 'local') and the `sync_meta` key/value table used by `pull-cloud`. The cloud has no `origin` column, so it is never in `CrlaAssessment.toMap()`; the SQLite `upsertWithId` and `pull-cloud` set it to 'cloud'. v11 rebuilt `crla_part2_fluency` to widen the comprehension CHECK to 0..7 (`_rebuildCrlaPart2ForV11`, runs before the CRLA creators). `onCreate` builds everything; `onUpgrade` re-runs the CRLA creators unconditionally at the end (all `IF NOT EXISTS`), after the schools rebuild, so new CRLA objects appear on upgrade. **Do not put new-table creators inside `if (oldVersion < N)` blocks that existing installs skip.** Bump the version when adding anything.
- Order matters: regions → students/schools/sections/enrollments → users → CRLA tables (they reference schools, students, sections, users).
- SQLite can't do `BEFORE INSERT` row rewrites, hence the attempt_no pattern above. Generated columns are avoided (need SQLite ≥ 3.31, which older Android lacks): totals, reading levels and wpm are computed by `AFTER INSERT` / `AFTER UPDATE OF <score cols>` triggers that write only the computed columns, so they cannot loop.
- The fluency insert trigger runs only `WHEN NEW.wpm IS NULL`, so rows mirrored from the cloud keep the cloud's wpm. Postgres and SQLite can differ by 0.1 at rounding boundaries; the cloud value wins. The CRLA Part 1/2 tables (and `enrollments`, one per learner per year) are still mirrored with `INSERT OR REPLACE`: their primary key is their only unique key, and an UPDATE would re-run the compute triggers over the cloud's wpm/totals. Since v14 the Part 1 triggers no longer touch `reading_level`, so a mirrored row keeps the cloud's level. Mirrored `crla_assessments` keep their id, `attempt_no`, snapshot and profile.
- **Local foreign keys are off on purpose** (`PRAGMA foreign_keys` is never enabled). The local DB is a role-scoped partial copy: e.g. `users.created_by` and `crla_assessments.administered_by` can point at users the signed-in account can't read, so enforcing FKs would break `pull-cloud`. The cloud enforces them. Never write mirrors with INSERT OR REPLACE on tables with secondary UNIQUE keys or child rows.
- `crla_results` also exists as a SQLite view with the same column names as the Postgres one; both read the stored `reading_profile`.
- Anything changed here must keep local and cloud behavior symmetric (offline and cloud attempt numbering, CHECKs and triggers must agree).

## Sync bookkeeping (SQLite v34; spec `docs/superpowers/specs/2026-10-20-sync-design.md`)
- The 18 synced tables (`syncedTables` in `data/local/sync_local_schema.dart`) carry `row_version`: NULL = new on this device, not NULL = copy of a server row (0 = pulled before v34, version unknown).
- **Every new row in the 14 id-keyed synced tables gets `'id': await nextLocalId(db)`** (`sync_local_writes.dart`; -1, -2, ... one countdown, never reused). A trigger refuses a new row with a positive id. Lists that order by id use `(id < 0), abs(id)`.
- Edits/deletes of server rows are journaled in `sync_changes` by triggers; ops the server refuses are refused locally (`crla_assessments` and `phil_iri_gst_results` insert-only, except the CRLA `reading_profile`; CRLA parts never deleted). Rows in `sync_pending` (an upload awaiting a decision) can't change, and no child can be added under them (`pendingLockMessage`: "This record is waiting for approval. Withdraw the upload to change it.").
- Cloud rows copied down outside a pull go through `mirrorSyncedRow` (not `upsertById`); the pull runs under `withSyncBypass`. The bypass only exists inside a transaction.
- A table rebuild must copy `row_version` and run before `createSyncLocalSchema` (called last), which recreates the sync triggers.

## Assessment rounds (one list per layer, changed together)
- An instrument's rounds live in: the Dart enums `PhilIriRound` / `CrlaRound` (`calendarRounds` in `services/calendar_rules.dart` is BUILT from them, never edited by hand); the cloud checks `phil_iri_assessments_round_check` / `crla_assessments_round_check`; and the calendar pairing `assessment_calendar_round_pairing` (migration 20261019050000), which must list exactly the same rounds.
- **Changing an instrument's rounds = the enum + ONE migration** that swaps the assessment table's round check and the calendar pairing together, converting (or deleting, owner's call) existing `assessment_calendar` rows first; the migration must refuse while unconverted rows exist (as 20261019050000 does), never delete silently. Every place that holds round names:
  - cloud: `phil_iri_assessments_round_check`, `crla_assessments_round_check`, `assessment_calendar_round_check` (names only, 20261019030000) + `assessment_calendar_round_pairing`, `aral_enrollments_basis_round_check` / `_suggestion_round_check`;
  - local SQLite: `phil_iri_local_schema.dart` (phil_iri_assessments.round), `local_database.dart` (crla_assessments.round, two places), `calendar_local_schema.dart` (round names), `aral_local_schema.dart` (basis_round, suggestion_round) — a CHECK change there needs a table rebuild and a version bump;
  - Dart: the enums; console argument lists in `crla_commands.dart`, `crla_import_commands.dart`.
- **Ship the app update before (or with) the migration.** An older app cannot pull data in a round it doesn't know: its local round CHECKs (assessment tables; the calendar's name list for a brand-new name) roll the whole `pull-cloud` back (nothing lost, cryptic error). Until a version gate exists (sync design), every device must update.
- The local `assessment_calendar` has NO pairing check on purpose (exception to "CHECKs agree"): it buys only the narrow case of an existing round name re-paired before any assessment uses it, and avoids a third failure point. Rows the app doesn't know are ignored on read (`RoundCalendarViewModel.effectiveCalendar`), listed as INVALID by `calendar-show` (`invalidWindows`; mainly an updated app holding an old local copy until its next pull), and `pull-cloud` warns when it gets them.

## Supabase specifics
- `crla_assessments.administered_by` is a `users.id` (uuid, handled as a String). ViewModels set it from the signed-in user (for the local DB); the cloud overwrites it with `auth.uid()` in `crla_assessments_before_insert`.
- Cloud INSERT into `crla_assessments` requires `sections.school_id = school_id` and an **active** enrollment of the learner in that section for that `school_year` (any role), on top of the role scope.
- Postgres `date` columns come back as ISO strings; `birth_date` and `assessed_at` are `String` in models. `CrlaViewModel` writes `assessed_at` as the local calendar date (yyyy-MM-dd), never a UTC timestamp.
- Soft rule: ask for the real schema/policy text (or a read-only query the owner can run) before assuming anything about columns, constraints, triggers, or RLS you haven't seen. The schema dump omits table-level CHECKs, view options and policies.
